When using the least squares method to predict the streamflow index, the response vector y needs to have compatible shapes with X because X will multiply with a beta_hat vector. When doing matrix computations, your dimensions matter so, y has a shape of (125,) (where 125 is the number of observations) and X has a shape of (125, 4) (where 125 is the number of observations and 4 is the number of predictors (including the intercept)) so our beta_hat should have a shape of (4,). When it comes to the intercept column in the design matrix (X), it is important to include because when computing the beta_hat matrix, if no intercept column is computed, no beta_0 coefficient will be computed. Standardizing the predictors helps reduce multicollinearity between one another, makes every predictor have a mean of 0 and a standard deviation of 1, and makes the predictors more comparable since they are all on the same scale. Broadcasting makes this standardization possible because it allows our code to work with the whole numpy array at once and apply different operations using other numpy arrays that have a compatible shape. So when standardzing the predictors, broadcasting the mean to be subtracted from the predictors and then using broadcasting to divide this difference by the standard deviation, allows for a faster more efficient way to standarize predictors without using a Python loop (which could take longer).

X @ beta_hat represents the matrix multiplication between the design matrix X and the estimated coefficients for the intercept and predictors. Due to how least squares computes estimates for coefficients of predictors, when you take the partial derivative with respect to beta_0 of the sum of squared errors and set it to 0 (to minimize it), the math works out to where the sum of residuals = 0. Then, when you take the mean of the residuals (sum of residuals/n), it should in theory equal 0 since the sum of residuals should be approximately equal to 0. The RMSE summarizes the size of prediction errors (on average) and penalizes the larger errors (due to squaring large residuals). Lastly, X * beta_hat computes element wise multiplcation between the two matrices (which is not correct) so in order to correctly muliply X and beta_hat, you need to do X @ beta_hat which does a dot product of the entries in the row with the entries of a column, that dot product becomes the entry for the resulting matrix.

The reason why we should verify that Q @ R should approximately equal X is because Q is a matrix with orthonormal columns and R is an upper triangular matrix. When Q and R are mulitplied through matrix multiplcation, we should be getting back our original design matrix, if we do not, that could mean the QR decomposition was not done correctly and is not preserving all the information in the original design matrix. In order to check that Q is orthonormal, we need to verify that Q.t @ Q approximately equals I, if it does than Q is orthonormal. When it comes to singular values, they are returned from largest to smallest. The large values are indicative of strong directions in the matrix and the small values are indicative of weak directions in the matrix. A large condition number means can indicate that the design matrix might be difficult to work with because the data is sensitive to changes (meaning small changes to the data can effect the resulst signficicantly), this can be seen in design matrices that have linear dependent predictors. In this analysis, when comparing the condition number for the raw design matrix (X_raw) and the standardized design matrix (X), the condition number for the raw design matrix was np.float64(3321.1189367925913) and the condition number for the standardized design matrix was np.float64(3.2951050664290027), which is a major decrease after standardization. When it comes to the raw condition number, measurement scale matters because different predictors are measured on different scales (in the case of this analysis, the predictors are measured in percentages, mm, and degrees Celsius), without standardization, the condition number could be inflated since each predictor (or column) has different scales, since the condition number is calculated using the largest singular value and dividing it by the smallest singular value. Based on the condition of the standardized design matrix, which is np.float64(3.2951050664290027), this is a pretty small condition number which means it is not likely that there is sever near-redudnancy in predictors in the standardized design matrix.

Reproducibility and Numerical-Computing Reflection

When working on a computational report, having a clean execution matters because you want your report to be reproducible, professional, and helps others understand your analysis. One way to have clean execution is to not write reusable code in a hidden notebook state. Having reusable code in a hidden notebook state can be confusing or make it hard to troubleshoot your code for people reading your computational report. This is because the reusable code that would be referenced in the computational report would not be explicitly stated in the computational report so if someone just had your computational report, the ability to troubleshoot and have a readable, reproducible report decreases.

When it comes to having an analysis that has efficient code, when trying to find least squares estimators, using np.linalg.lstsq() is preferable because it uses optimized numpy operations and stable algorithms that directly apply to the whole numpy arrays. This is preferable when compared to doing the matrix computation “by-hand” because that method computes all of the matrix multiplication “by-hand” and can take a longer time. When it comes to QR decomposition and SVD reconstruction, using checks like np.allclose() is preferable to exact equality because there is rounding involved when calculating the QR decomposition and the SVD reconstruction. If we used exact equality, we are most likely going to get False so using checks like np.allclose() checks if our QR decomposition or SVD reconstruction are close to the values they need to be (within a range that allows for rounding errors from calculations). When learning about the condition number that is related to SVD reconstruction, I learned that standardizing the design matrix can help with fixing a linear model that has linearly dependent predictors, unstable coefficient estimates, and sensitivity to changes, which are all associated with large condition numbers.
Standardizing also helps with predictors of different scales, these predictors with different scales can artificially inflate the condition number so standardizing puts them all at the same scale. When the predictors are all on the same scale (after being standardized), their estimated coefficients are more comparable.

When it comes to reproducibility in this report, I think one thing that I will carry into the final project is not manually referencing code. I think this is really helpful because if I make changes to my code (but it is still assigned to the same variable), my writing is going to be updated since I am referencing the code in my writing instead of manually writing the result. I also liked having the setting code-fold: true in the beginning of the quarto markdown because in my html, if someone needs to see the code, they can see it but if they don’t want/need to, it can be collapsed so it isn’t taking up a majority of the report. This has also been helpful with troubleshooting on my end when using the preview command because when writing in quarto markdown it can be hard to see where I have made mistakes so if I need to see my code and what I need to trouble shoot, having the code easily accessible is nice and makes my report more reproducible.
